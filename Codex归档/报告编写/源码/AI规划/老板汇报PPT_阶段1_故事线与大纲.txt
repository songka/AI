《内部 AI 框架与工业 Skill 建设规划》
阶段 1：证据分析、SCR 故事线与逐页大纲（待确认）

一、沟通任务
汇报对象：公司老板/管理层。
汇报目的：申请批准“统一内部 AI 框架 + 受控 Skill Hub + AS228T PLC 首个样板”的建设方向、责任分工和规则资料投入。
管理层应带走的结论：AI 能力不能继续依赖个人提示词和零散客户端；应由公共模型服务承载统一入口，由 Skill Hub 固化公司工程规则，并以台达 AS228T 的三件套输出（全局变量、局部变量、ST 程序）验证可复制性。

E07｜现有 110 个 Markdown 中没有 AS228 或 AS228T 命中。
来源：对 package 的全文检索。
置信度：高。
含义：当前包没有目标 PLC 的型号专属知识。
推荐视觉：红色缺口标记。

E08｜通用 ST 风格文件明确写明“phase-1 Mitsubishi FX3U + GX Works2”，并非通用 IEC/台达 AS 风格。
来源：references/common/st-style-guide.md。
置信度：高。

推荐视觉：规则冲突示意。

E09｜现有输出规则只要求“变量/设备分配建议 + ST 代码或伪代码”，没有把全局变量、局部变量、ST 主程序定义为强制、分离、可校验的三件套。

置信度：高。
含义：需要新增固定输出契约和完整性校验。

E10｜现有 IDE 集成材料给出台达 ISPSoft CSV 变量表样例，但未证明 AS228T 的完整导入格式、字段和编译兼容性。
来源：references/common/ide-integration-formats.md。
置信度：中（方向可用，型号兼容性待官方资料验证）。
含义：首期先确保可审阅、可复制；可导入格式需用真实 ISPSoft 工程验证后再承诺。
推荐视觉：成熟度阶梯。

E11｜AI规划目录未发现公司现有地址分配、变量命名、程序框架等规则文件。
来源：AI规划目录盘点。
置信度：高（当前目录范围内）。
含义：这些规则必须由业务团队提供并作为版本化 reference；PPT 中不得虚构具体号段或命名法。
推荐视觉：待补资料清单。

三、冲突、缺口与 caveat

1. 型号资料缺口：没有 AS228T 硬件手册、编程手册、ISPSoft 版本、现有工程样例。
2. 公司规则缺口：地址分配表、变量命名规范、程序组织/调用顺序、注释规范、报警/互锁/复位规则尚未提供。
3. 验收基准缺口：尚未给出“可编译、功能正确、规则合规”的测试用例和判定人。
4. 平台边界缺口：公共电脑规格、并发人数、网络隔离、账号权限、数据保留策略未提供；PPT 只做原则性架构，不做容量承诺。
5. 其他 Skill 缺口：机器人、PC、视觉、办公类尚无清晰输入输出、责任人和样例，先按组合规划，不宣称已具备。
6. 术语核对：用户写作 AS228t；正式页统一写“台达 AS228T”，最终需以铭牌/项目型号确认大小写和完整后缀。

四、三条备选故事线

A｜治理先行、PLC 样板验证（推荐）
核心结论：统一入口和规则治理是内部 AI 可用的前提，AS228T 是最适合先做深做透的样板。
Issue tree：为什么要统一 → Skill Hub 管什么 → 先做哪些 Skill → AS228T 如何保证输出 → 如何验收和复制。
关键证据：E01-E11。
优势：同时回答老板最关心的价值、风险、投入、责任和第一步成果；不依赖尚未提供的 ROI 数字。
风险：需要管理层指定规则 Owner 并协调工程资料。

B｜技术架构蓝图
核心结论：以公共 DeepSeek 为推理底座、Skill Hub 为规则层、个人客户端为入口，构成内部 AI 技术平台。
Issue tree：客户端、网关、模型、Skill、知识库、审计。
优势：架构直观，适合技术评审。
不推荐原因：对老板而言容易变成“买机器/装模型”的 IT 项目，弱化规则资产和组织责任。

C｜AS228T 单点突破
核心结论：先把 PLC 三件套自动生成做成，再扩展其他 Skill。
Issue tree：现有包差距 → AS228T 规则 → 三件套 → 编译/评审 → 复制。
优势：成果具体、验收清晰。
不推荐原因：无法完整回答公共 AI 框架、跨域 Skill 分配和长期治理问题。

推荐：采用 A，以 B 的架构图和 C 的 PLC 深潜作为中段证据。

五、推荐 SCR

Situation：公司已有个人 AI 客户端、公共 DeepSeek 和 Skill Hub 的雏形，并已识别 PLC、机器人、PC、视觉、办公五类需求。
Complication：目前能力仍是“入口有了、规则未固化”；现有 PLC Skill 宽而浅、没有 AS228T 专属知识，且公司地址/命名/框架规则尚未进入可版本化、可测试的知识层。
Resolution：批准“统一内部 AI 框架 + 受控 Skill Hub”，分阶段建设；先以 AS228T Skill 为 P0 样板，强制输出全局变量、局部变量、ST 程序，并通过规则检查、工程评审和真实项目回归后再复制到其他领域。

六、逐页大纲、图表计划与组件清单（建议 16 页，16:9）

P1 封面｜角色：开场
结论标题：《内部 AI 框架与工业 Skill 建设规划》
副标题：从个人工具试用走向可治理、可复用、可验收的工程能力。
证据：E01-E03。
视觉：极简标题 + 抽象“中央能力节点连接工程终端”主视觉。
密度：低；标题区 1、副标题 1、日期/汇报部门 1。
组件：标题、副标题、主视觉、页脚。

P2 管理层决策｜角色：Situation → Complication
结论标题：当前最需要批准的不是更多 AI 客户端，而是一套统一治理的能力底座。
论证：已有入口和模型雏形；真正决定可用性的，是 Skill 规则、责任人、版本、评审和审计。
证据：E01-E03、E11。
Caveat：未量化当前返工和效率损失。
视觉：左侧“已有”/右侧“缺口”对照，中间给出三项决策请求。
密度：4 区；主对照 65%，决策侧栏 35%；1 个 SO WHAT。
组件：现状清单、缺口清单、决策框、SO WHAT、页脚。

P3 现状诊断｜角色：Situation
结论标题：个人端—公共模型—Skill Hub 的雏形已经形成，但关键控制面尚未建立。
论证：重绘用户草图；在访问路径之外增加缺失的认证、版本、日志、权限、发布、回滚标记。
证据：E01、E02。
Caveat：缺失项是基于架构审视的建议，不代表当前系统一定完全没有。
视觉：现状架构图，绿色表示已知，橙色虚线表示待确认/待建设。
密度：3 区；主图 75%，风险侧栏 25%；6 个标注。
组件：架构图、风险标注、图例、SO WHAT、来源页脚。

P4 目标架构｜角色：Resolution
结论标题：目标架构应把“模型能力、公司规则和个人入口”解耦，Skill Hub 成为唯一受控能力层。
论证：五层——个人客户端/统一接入、模型服务、Skill 编排、规则与模板库、治理与审计；工程数据按权限进入。
证据：E01-E03；其余为规划建议。
Caveat：不承诺具体并发和硬件容量。
视觉：分层架构 + 一条从请求到输出的控制流。
密度：5 层 + 1 侧栏；主图 78%，原则侧栏 22%。
组件：五层架构、箭头、4 条治理原则、SO WHAT、页脚。

P5 Skill 组合与优先级｜角色：Resolution
结论标题：先做规则清晰、输出可验收的工程 Skill，再扩展高复杂度和通用办公场景。
论证：P0 AS228T PLC；P1 机器人分品牌、PC 标准框架、视觉二次开发；P2 办公类。五类能力统一纳入 Skill Hub，但采用不同的输入契约、风险等级和验收门。
证据：E02、E03；优先级为规划建议。
视觉：价值 × 可标准化程度矩阵 + 能力表。
密度：4 区；矩阵 60%，能力表 40%；5 类 Skill、3 个优先级。
组件：二维矩阵、Skill 标签、优先级图例、侧栏说明、SO WHAT。

P6 机器人 Skill｜角色：Resolution
结论标题：机器人能力应采用“共性工程层 + 品牌专精层”，那智、Fanuc、川崎分别维护，禁止混用指令和坐标语义。
论证：共性层固化工艺流程、点位表、I/O 握手、报警恢复、节拍与安全边界；品牌层分别承载工程结构、指令、坐标系、程序格式、备份恢复和调试清单。
建议输出：程序骨架、点位/坐标清单、I/O 握手表、报警与恢复逻辑、调试/验收清单；任何安全相关输出必须由现场工程师确认。
证据：E03；具体品牌规则资料尚未提供。
Caveat：不得在没有机器人型号、控制柜版本、工具/用户坐标和工艺信息时生成可直接下发的程序。
视觉：一层共性底座托起三个品牌模块，右侧展示统一输出契约。
密度：5 区；共性层 30%、品牌层 45%、输出与边界 25%。
组件：共性层、3 个品牌模块、输出清单、风险边界、SO WHAT。

P7 PC 程序 Skill｜角色：Resolution
结论标题：PC 程序 Skill 的价值是让新项目默认落入公司标准框架，而不是每次从空白代码开始。
论证：固化项目目录、配置管理、日志、异常处理、设备通信抽象、数据库/接口、权限、测试、打包发布和代码评审规则；按公司主技术栈再拆框架模板。
建议输入：业务需求、技术栈、设备接口、数据流、部署环境、非功能要求。
建议输出：项目骨架、模块清单、接口契约、关键代码、配置样例、测试用例、部署说明和评审清单。
证据：E03“PC 程序：标准框架”；具体框架与语言待提供。
Caveat：未确认技术栈前只定义框架契约，不预设 C#、Python、C++ 或 Web 技术方案。
视觉：标准框架剖面图 + 从需求到可运行骨架的流水线。
密度：6 个框架层、3 类输入、7 类输出。
组件：架构剖面、输入输出、模板库、质量门、SO WHAT。

P8 视觉程序 Skill｜角色：Resolution
结论标题：视觉 Skill 应聚焦“基于现有相机/算法平台的二次开发闭环”，把选型、标定、算法和 PLC/PC 接口统一起来。
论证：覆盖需求澄清、硬件/SDK 信息、光学与标定、采图、算法流程、结果判定、通信协议、异常处理、节拍评估和现场验证；按实际视觉平台拆子 Skill。
建议输出：视觉流程图、参数/标定表、算法模块、接口定义、结果码表、异常与重试策略、测试图集要求、验收清单。
证据：E03“视觉程序：二次开发程序”；具体品牌、SDK 和样例待提供。
Caveat：没有真实图像、镜头/光源、节拍和误判漏判指标时，不承诺算法效果。
视觉：采图—处理—判定—通信—追溯闭环。
密度：5 阶段、7 类输出、1 个数据闭环侧栏。
组件：闭环流程、输入条件、输出清单、风险边界、SO WHAT。

P9 办公类 Skill｜角色：Resolution
结论标题：办公 Skill 应优先解决高频、低风险、可复核的文档工作，并通过模板和权限边界控制信息质量。
论证：建议拆为报告/制度文档、表格分析、PPT 汇报、会议纪要与任务提取、内部知识检索五类；共用公司模板、术语表、密级、审批和引用规则。
建议输出：可编辑 DOCX/XLSX/PPTX、摘要、行动项、引用清单；外发、发送、删除等动作必须二次确认。
证据：E02“办公类”；具体办公场景待补。
Caveat：不能把未经核验的 AI 结论直接作为经营数据或正式制度发布。
视觉：高频 × 风险矩阵，标注首批办公场景。
密度：5 类场景、4 条共性规则、3 级风险。
组件：场景矩阵、模板层、权限边界、输出清单、SO WHAT。

P10 组织分工｜角色：Resolution
结论标题：每个 Skill 必须同时拥有业务 Owner、规则维护人和验收人，平台团队只负责机制不替代工程判断。
论证：平台负责人、PLC Owner、三类机器人品牌 Owner、PC 程序 Owner、视觉程序 Owner、办公 Owner、验收人和使用者；按 RACI 表划分规则编写、样例脱敏、测试、评审、发布、反馈和回滚。
证据：规划建议；E11 支持必须明确规则 Owner。
Caveat：具体姓名待老板指定。
视觉：简洁 RACI 表 + 发布责任链。
密度：主表 70%，角色说明 30%；8 类角色 × 7 项活动。
组件：RACI 表、角色说明、升级路径、SO WHAT、页脚。

P11 PLC 现状审计｜角色：Complication
结论标题：现有 PLC 包“素材丰富但目标错位”，必须从十厂商通用包裁剪为 AS228T 单型号专精 Skill。
论证：111 文件/10 厂商 vs 台达仅 3 文件；无 AS228T 命中；通用 ST 风格指向三菱 FX3U。
证据：E04-E08。
视觉：数字带 + 宽而浅/窄而深对照 + 规则冲突红标。
密度：5 区；3 个关键数字、1 个对比图、1 个风险侧栏。
组件：关键数字、对比图、证据注释、风险框、SO WHAT。

P12 AS228T Skill 产品定义｜角色：Resolution
结论标题：AS228T Skill 的首要产品不是“回答 PLC 问题”，而是稳定生成可评审的三件套工程包。
论证：输入需求/I-O/工艺/规则 → 完整性检查 → 地址与命名规则 → 程序框架选择 → 生成 → 静态检查 → 人工验收。
强制输出：①全局变量表 ②局部变量表 ③ST 程序；附假设、风险、测试清单。
证据：E09、E10；三件套来自用户要求。
视觉：端到端流水线，三件套在右侧展开。
密度：6 阶段 + 3 输出卡；主流程 70%，输出 30%。
组件：输入契约、流程箭头、三件套、失败回路、SO WHAT、页脚。

P13 公司规则注入｜角色：Resolution
结论标题：公司规则必须以独立、可版本化的 reference 进入 Skill，优先级高于通用模板且禁止模型自行补齐。
论证：至少四类规则——地址分配、变量命名、程序框架、控制模式；每类有 Owner、版本、适用范围、正反例和冲突处理。
证据：E11；规则类别来自用户要求及现有包缺口。
Caveat：具体规则内容待提供。
视觉：规则优先级金字塔 + reference 文件结构树。
密度：4 类规则、4 个元数据字段、1 个优先级链。
