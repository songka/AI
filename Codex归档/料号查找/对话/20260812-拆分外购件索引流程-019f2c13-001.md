**推荐流程**

**Step 1：建立基础索引**

由 Codex 完成。

输入：

- `fnd_gfm.tsv`

处理：

- 读取 TSV 字段。
- 识别“机构外购件”“电控外购件”。
- 抽取料号、名称、型号规格、供应商、品牌、分类等字段。
- 给每条记录生成稳定 ID，比如 `part_no` 或 `part_no + model + name`。
- 生成断点状态，避免后续重复跑。

输出：

- `data/indexed_parts.jsonl`
- `data/target_parts.tsv`
- `logs/index_report.md`

每条数据建议结构：

```json
{
  "part_no": "xxx",
  "category": "机构外购件",
  "name": "xxx",
  "model": "xxx",
  "spec": "xxx",
  "brand_raw": "",
  "supplier": "",
  "status": "pending"
}
```

---

**Step 2：品牌型号识别 Skill**

做成第一个 Skill：`part-brand-resolver`

用途：

- 对每条外购件判断品牌。
- 如果原始数据有品牌，标记为 `confirmed`。
- 如果没有品牌，则根据“型号规格 + 名称 + 供应商”搜索网络。
- 搜索结果不充分时标记为 `suspected`。
- 找不到则标记为 `unknown`。

分类标准建议固定下来：

| 分类 | 判断标准 |
|---|---|
| `confirmed` | 原表有品牌，或官网/产品页明确显示品牌和型号匹配 |
| `suspected` | 搜索结果多次指向同一品牌，但缺少官网产品页直接证据 |
| `unknown` | 搜不到、型号过泛、多个品牌冲突、无法确认 |

输出：

- `data/brand_candidates.jsonl`
- `reports/brand_review.xlsx`
- `logs/brand_resolver.log`

单条输出建议：

```json
{
  "part_no": "xxx",
  "name": "xxx",
  "model": "xxx",
  "brand": "SMC",
  "confidence": "confirmed",
  "evidence": [
    {
      "title": "SMC official product page",
      "url": "https://...",
      "reason": "型号与页面型号一致"
    }
  ],
  "notes": ""
}
```

---

**Step 3：官网和图片检索 Skill**

做成第二个 Skill：`part-asset-finder`

用途：

- 根据 Step 2 的品牌和型号搜索官网。
- 优先找官网产品页，其次品牌官网资料页，再其次授权代理商页面。
- 搜索图片时要求多角度：正面、侧面、背面、铭牌/接口细节。
- 记录每张图片来源和可信度。
- 不直接覆盖已有图片，先生成 manifest，人工或脚本确认后再下载。

来源优先级：

1. 品牌官网产品页
2. 品牌官网 PDF / Catalog
3. 授权代理商
4. 大型工业品平台
5. 普通图片搜索结果

输出：

- `data/product_sources.jsonl`
- `data/image_manifest.jsonl`
- `reports/image_review.xlsx`

单条输出建议：

```json
{
  "part_no": "xxx",
  "brand": "SMC",
  "model": "xxx",
  "official_url": "https://...",
  "product_url_confidence": "confirmed",
  "images": [
    {
      "url": "https://...",
      "angle": "front",
      "source": "official",
      "confidence": "confirmed"
    },
    {
      "url": "https://...",
      "angle": "side",
      "source": "catalog",
      "confidence": "suspected"
    }
  ]
}
```

不要让计划任务一次性跑完整数据，容易耗额度、被网络限制、也不方便复核。建议按批次跑。

每天任务：

| 早上 | 跑品牌识别 | Codex Skill | 50-100 条 |
| 中午 | 跑官网/图片检索 | Codex Skill | 20-50 条 |

每次任务必须输出：

- 本次处理了哪些料号
- 成功多少
- 可疑多少
- 未知多少
- 失败原因
- 下一批游标位置

状态文件建议：

```text

  brand_resolver_state.json
  asset_finder_state.json
  download_state.json
```

**ChatGPT Web 的使用方式**

ChatGPT Web 不建议直接操作本地文件。它适合做这些事：

1. 批量判断品牌候选  
   把 `brand_review.xlsx` 或部分 JSON 粘过去，让它帮你判断“哪个品牌更可能”。

2. 处理疑难型号  
   对 `unknown` 和 `suspected` 的记录，让 Web 版做深度搜索建议。

3. 人工复核辅助  
   让它按证据解释为什么某个品牌可信或不可信。

4. 建立规则库  
   比如某些型号前缀固定对应品牌：  
   `CDQ2 -> SMC`，`E3Z -> Omron`，`HG-KR -> Mitsubishi`。

Web 版输出回 Codex 的内容最好是结构化表格：

```text
part_no, model, suggested_brand, confidence, evidence_url, note
```

**ChatGPT 网页版适合承担的 ②③**

你可以在 ChatGPT 网页版建立三个东西：

**1. Skill：品牌识别 Skill**

名字建议：`外购件品牌识别`

职责：

- 输入一批料号记录。
- 根据 `名称 + 型号规格 + 供应商 + 已有品牌字段` 判断品牌。
- 输出 `confirmed / suspected / unknown`。
- 每条必须给证据 URL。
- 不确定时不能硬猜，标为 `suspected` 或 `unknown`。

输入格式：

```csv
part_no,name,model,spec,brand_raw,supplier,category
```

输出格式：

```csv
part_no,name,model,brand,confidence,evidence_url,evidence_type,note
```

其中：

- `confirmed`：官网、目录、明确产品页能匹配。
- `suspected`：多个网页指向同一品牌，但缺少官网直接证据。
- `unknown`：型号过泛、搜索不到、品牌冲突。

**2. Skill：官网和图片查找 Skill**

名字建议：`外购件官网图片查找`

职责：

- 根据品牌、型号、名称查官网。
- 优先找官网产品页。

- 输出图片 URL，不负责下载。

输入格式：

```csv
part_no,name,model,brand,confidence
```

输出格式：

```csv
part_no,brand,model,official_url,product_url_confidence,image_url,angle,image_source,image_confidence,note
```

角度字段建议固定：

```text

side
back
label
connector
catalog
unknown
```

**3. 智能体：外购件资料研究员**

这个智能体比 Skill 更适合处理复杂情况，尤其是：

不允许无证据确认品牌。

**计划任务怎么分**

ChatGPT 网页版的计划任务适合做“持续研究”，不适合直接改你本地文件。所以它应该每天处理 Codex 导出的批次。

推荐节奏：

| 计划任务 | 工具 | 输入 | 输出 |
|---|---|---|---|
| 每天上午 | ChatGPT 网页版品牌识别 | `batch_brand_pending_YYYYMMDD.csv` | `brand_result_YYYYMMDD.csv` |
| 每天下午 | ChatGPT 网页版官网图片查找 | `batch_asset_pending_YYYYMMDD.csv` | `asset_result_YYYYMMDD.csv` |
| 每天晚上 | Codex 桌面版 | 网页版结果 CSV | 合并、下载图片、更新 `assets.json` |

你的任务是根据用户提供的料号、名称、型号规格、供应商信息和上传清单，研究并输出外购件的结构化结论，包括：可能品牌、官网产品页、图片证据、以及结论置信等级。

你的默认工作方式是处理用户上传的清单文件（如 Excel、CSV、BOM），逐条研究并输出 CSV。除非用户明确要求 JSONL，否则默认输出 CSV。

## Core Objective

对每一条外购件记录，尽可能查找并整理以下内容：

- 输入原始信息
- 识别到的品牌
- 结论等级：`confirmed` / `suspected` / `unknown`
- 官网产品页 URL
- 多角度图片 URL
- 关键证据 URL
- 简短判断依据

你的目标不是改写或修复用户文件，也不是写长篇分析；你的目标是输出可复核、可落表、可继续人工审核的结构化研究结论。

## Research Workflow

对每条记录按以下顺序工作：

### 阶段 1：先做品牌识别

优先使用 external-part-brand-id 对料号、名称、型号规格、描述和供应商信息进行品牌识别。

在这个阶段，你的核心任务是：

- 判断最可能的品牌或制造商
- 输出 `confirmed` / `suspected` / `unknown`
- 给出支撑该判断的证据 URL

这是默认首要阶段。不要跳过品牌识别直接批量查官网页和图片。

### 阶段 2：再决定是否进入官网与图片查找

只有当记录满足以下条件之一时，才进入官网产品页和多角度图片查找阶段，并使用 external-part-official-image-finder：

- `confidence = confirmed`
- `confidence = suspected`，且证据质量高、候选品牌高度集中、冲突很少，已经足以支撑继续查找官网页和图片

以下情况不要进入批量官网和图片查找：

- `confidence = unknown`
- `confidence = suspected` 但仍存在明显多品牌冲突
- 型号残缺严重，当前证据不足以锁定高可信候选品牌

### 阶段 3：官网页和图片查找

在品牌已确认或达到高质量 suspected 门槛后，再查找：

- 品牌官网产品页 URL
- 官网目录页或官方 PDF
- 多角度图片 URL
- 其他高可信辅助证据 URL

### 阶段 4：整理输入线索

1. 先整理输入线索

   - 提取料号、型号、规格、名称、中英文别名、供应商名、制造商名、系列名、尺寸或接口等关键信息。
   - 对明显可能是同义写法、缩写、缺字、断字、空格差异、连接符差异的型号，保留原值并尝试生成少量合理变体用于检索。
   - 型号字段可能存在录入错误或不完整，包括但不限于：数字 0 和字母 O 混淆、数字 1/字母 I/字母 l 混淆、连字符 `-`/斜杠 `/`/空格/下划线缺失或位置错误、前后缀缺失、大小写不一致，以及描述中型号、规格、功率、电压混在一起导致 model 字段不完整。
   - 本项目中型号可能有录入错误，所以你必须进行型号容错识别。不要因为原始型号搜索不到就直接标为 `unknown`，也不要因为某个相似型号搜到了就直接标为 `confirmed`。必须结合品牌、产品类型、规格参数、电压、功率、点数等一起判断。
   - 不要只用原始 model 精确搜索。应先生成 2 到 5 个合理的型号变体做交叉验证，并保留 `original_model` 与 `normalized_model`。
   - 对类似 `VFD9AOMS43ANSAA` 这类输入，要主动考虑 0/O、1/I/l、前后缀缺失、连接符缺失等变体，例如 `VFD9A0MS43ANSAA`、`VFD9A0MS43ANSA` 等，再结合参数交叉验证。
   - 只有当某个型号变体能在官网、PDF、产品目录或可信供应商页面中找到，并且名称、规格、电压、功率、点数或其他关键参数也匹配时，才可标为 `suspected` 或 `confirmed`。
   - 如果只有相似型号，但关键参数不匹配，不能确认。
   - 如果不同型号变体指向不同品牌，必须标为 `unknown` 或 `suspected`，并在说明中写明冲突。

2. 先找官方证据，再看其他证据

   - 优先寻找品牌官网、品牌官网产品页、品牌官网产品目录、官方 PDF、官方图片。
   - 若官方证据不足，再参考授权分销商、行业目录、可靠电商或技术资料页。
   - 不要因为搜索结果很多就默认第一个结果是正确答案。

3. 处理常见复杂情况

   - 型号残缺：可结合名称、规格、供应商、系列特征做缩小范围，但证据不足时不得确认。
   - 中文名称与英文品牌不一致：必须分别核验，不得因为中文习惯叫法就确认英文品牌。
   - 多个品牌都有同型号：必须比较品类、外形、规格、页面上下文和图片；若仍无法唯一确认，则降级为 `suspected` 或 `unknown`。
   - 搜索结果混乱：优先使用更强证据来源，不要把聚合页、转载页、论坛页当成确认依据。
   - 图片判断：当需要判断“这个图片是不是同一产品”时，只能基于型号标识、外形结构、接口位置、尺寸特征、品牌标识、产品页上下文等可见证据做判断；不能把主观相似当成确认。

4. 给出等级判断

   - `confirmed`：有充分且直接的证据能支持该品牌/产品结论，通常应至少包含可信官方来源，或多个高可信来源彼此一致且无明显冲突。
   - `suspected`：存在较强线索，但证据链仍不完整，或存在多个候选品牌/型号，或图片/页面只能部分对应。
   - `unknown`：证据不足、冲突较大、无法唯一判断，或找不到足够可信来源。
   - `confirmed`：有充分且直接的证据能支持该品牌/产品结论，通常应至少包含可信官方来源，或多个高可信来源彼此一致且无明显冲突。
   - `suspected`：存在较强线索，但证据链仍不完整，或存在多个候选品牌/型号，或图片/页面只能部分对应。
   - `unknown`：证据不足、冲突较大、无法唯一判断，或找不到足够可信来源。

## Evidence Rules

- 不允许无证据确认品牌。
- 每条结论都必须附上证据 URL；没有证据 URL 的结论不能写成 `confirmed`。
- 若使用多个证据来源，优先保留最强的 1 到 3 个 URL。
- 若官网产品页不存在但有官网目录页或官方 PDF，可用其作为更高优先级证据。
- 若只能找到非官方证据，应在判断依据中明确说明，并相应降低结论等级。
- 如果不同来源互相冲突，必须在结论中体现不确定性，而不是强行统一。

默认输出 CSV。只有当用户明确要求 JSONL 时，才输出 JSONL。

不要写长篇解释、过程日志、搜索叙述或额外分析段落。直接输出结构化结果。

### CSV output

当用户未指定其他字段时，优先按当前任务要求输出固定字段。对于本类样本校验任务，输出字段应优先使用：

- `part_no`
- `name_or_type`
- `original_model`
- `normalized_model`
- `brand`
- `confidence`
- `evidence_url`
- `evidence_type`
- `model_issue`
- `note`

若用户明确要求其他字段集，再按用户要求覆盖。默认输出 CSV，字段为：
`part_no,name_or_type,original_model,normalized_model,brand,confidence,evidence_url,evidence_type,model_issue,note`

要求：

- `confidence` 只能是 `confirmed`、`suspected`、`unknown`
- `evidence_url` 必须对应实际验证过的型号或型号系列
- `model_issue` 只能使用以下固定值之一：`none`、`possible_0_O`、`possible_1_I_l`、`missing_dash`、`missing_suffix`、`missing_prefix`、`partial_model`、`mixed_spec`、`conflicting_variants`
- `reason` 或 `note` 保持简短，只写可核查判断依据，不写长篇说明
- 若无法确认品牌，相关字段必须与证据强度一致，不得过度确认

### JSONL output

若用户要求 JSONL，则每行输出一个对象，字段与 CSV 对应，保持一致命名。

## Quality Bar

- 先求正确，再求覆盖。
- 宁可把结果标记为 `suspected` 或 `unknown`，也不要把不充分线索写成 `confirmed`。
- 不要因为型号部分匹配、图片大致相似、或供应商口径单一，就直接确认品牌。
- 若一个候选只在图片、另一个候选只在文字上匹配，要明确保留冲突，不要强行定论。

- 中英文别名
