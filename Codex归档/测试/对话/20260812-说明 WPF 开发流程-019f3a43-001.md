## 助手

可以。我可以写 C# WPF 程序，也可以在本机工作区里尽量自己验证到可运行状态。

我的典型流程是：

1. **先看项目结构**
   - 用 PowerShell / `rg` / `Get-ChildItem` 查看 `.sln`、`.csproj`、`App.xaml`、`MainWindow.xaml`、MVVM 结构、资源文件等。
   - 判断是 .NET Framework WPF、.NET Core / .NET 6+ WPF，还是混合老项目。

2. **按现有风格改代码**
   - 编辑 `XAML`、`C#`、ViewModel、Model、服务类等。
   - 优先沿用项目已有模式，比如 MVVM、CommunityToolkit.Mvvm、Prism、ReactiveUI、手写 ICommand 等。
   - 手工编辑文件时我会用补丁工具，避免大范围误改。

3. **构建验证**
   - 如果项目支持，我会运行：
     - `dotnet build`
     - `msbuild`
     - `dotnet test`
   - 看编译错误、XAML 解析错误、资源路径错误、NuGet 还原问题等，然后继续修。

4. **运行或半自动验证**
   - WPF 是桌面 GUI，完全自动化会受环境限制，但我可以：
     - 启动程序检查是否崩溃
     - 查看控制台/构建输出
     - 检查生成目录里的 exe/dll
     - 如果可用，借助桌面/浏览器/截图类工具观察窗口
   - 如果需要打开 GUI 程序，有时会触发权限确认，因为这是在你的 Windows 桌面环境里启动应用。

5. **功能验证**
   - 对纯逻辑部分，我会优先加或跑单元测试。
   - 对 UI 交互，我可以检查绑定、命令、属性通知、资源引用、窗口启动路径。
   - 如果项目里已有自动化 UI 测试，我可以运行它们；没有的话，我会用构建 + 启动 + 关键路径检查来验证。

我会用到的主要工具：

- `PowerShell`：查看文件、运行构建、启动程序。
- `rg`：快速搜索代码。
- `apply_patch`：安全地修改源码。
- `.NET SDK / MSBuild`：编译、测试、发布 WPF 程序。
- `codex_app.load_workspace_dependencies`：如果涉及文档、表格、PDF 等附属文件时会用。
- 必要时用桌面控制/截图相关能力观察运行界面，但这取决于当前环境权限。

所以答案是：**可以写，也可以自己验证；验证深度取决于项目是否能在当前机器上构建、依赖是否完整、GUI 是否允许启动。**你给我一个 WPF 项目或需求，我可以直接开工。
