# 飞书自动签核工具开发经历与使用心得

## 一、项目概述

本项目最初只是一个用于登录签核平台、读取待签内容并自动提交的 Python 脚本。随着实际使用需求不断增加，项目逐步扩展为一套包含签核 CLI、飞书机器人、多用户配置、规则引擎、群通知、AI 辅助、统计网页和部署工具的完整签核系统。

本报告依据以下材料整理：

- `完整对话_原档.txt` 中导出的历史对话、调试记录和服务器日志；
- 当前 `deploy/auto-sign/` 程序；
- 项目说明书、部署说明和流程图；
- 2026 年 7 月 21 日至 24 日间留下的服务器调试记录与发布包。

需要说明的是，原始对话中的编号是导出记录编号，其中包含大量工具返回和日志，并不等同于 897 次独立需求讨论。

## 二、开发过程

### 1. 从单机脚本到签核工具箱

第一阶段的目标比较直接：解决“能登录、能查询、能签核、能拒签”的问题。项目在原有 HTTP 自动签核脚本上增加了命令行入口，并逐步形成登录、查询、详情展示、指定签核、指定拒签、全签、全拒和测试模式等命令。

这个阶段最重要的改进是加入了 `dry-run` 测试模式。它可以只抓取和判断，不向平台提交结果，为后续修改规则提供了安全的验证手段。

### 2. 建立规则引擎

随着料号类别、单位、描述、申请人等判断条件增多，固定写在代码中的判断逻辑已经难以维护，因此项目引入了规则文件和 AND/OR 多条件组合。

规则设计经历了明显演进：

1. 最初使用姓名白名单、姓名黑名单和内容白名单；
2. 后来允许签核、拒签和等待分别配置；
3. 再加入拒签优先、拒签理由以及模拟自动签核；
4. 最终将名单升级为“用户组”和“内容组”，规则通过组名引用成员，组改名时同步更新规则引用。

这种调整让业务规则从“修改代码”变为“修改数据”，普通用户可以直接在飞书卡片里维护。

### 3. 接入飞书

项目随后增加飞书发送 CLI、机器人消息回调和互动卡片，实现了：

- 私聊机器人查询待签内容；
- 通过明确指令签核或拒签；
- 群聊中通过 @机器人或 @指定用户触发查询；
- 自动操作成功后发送群通知；
- 规则、用户组、内容组和设置使用卡片查看与编辑；
- 自定义菜单直接打开帮助、查询、规则、组、设置和统计。

这一阶段不仅是增加一个消息入口，也促使程序从单用户脚本转向长期运行的服务。

### 4. 服务器部署与现场调试

系统部署到宝塔服务器后，先后遇到了 Python 版本、依赖安装、端口占用、反向代理、Cloudflare、回调格式和进程启动等问题。

典型问题包括：

- 系统 `python` 实际指向 Python 2.7 或 3.6，而项目需要 Python 3.9；
- Windows 文件换行和编码导致 Linux 执行异常；
- 7000 端口被旧进程占用；
- 反向代理配置造成 400、404 或 526；
- 飞书回调地址能够验证，但实际消息事件没有进入正确进程；
- Gunicorn 重启后仍加载旧文件或旧版本。

经过这些问题，部署方式逐渐固定为：宝塔 Python 项目使用指定的 Python 3.9.7 环境，Gunicorn 对外提供回调服务，计划任务每分钟检查一次各用户是否到达执行时间。

### 5. 多用户与数据隔离

实际使用中，不同飞书用户需要使用各自的签核平台账号、规则和时间设置，因此项目增加了以飞书 `open_id` 为唯一标识的多用户结构。

每个用户拥有独立的：

- `auth.json`：签核平台账号；
- `rules.json`：签核、拒签和通知规则；
- `groups.json`：用户组和内容组；
- `settings.json`：自动签核时间、间隔、等待和通知设置；
- 个人统计记录。

新用户默认没有签核规则、拒签规则和组，避免复制其他人的业务策略后产生误操作。

### 6. AI 从“执行者”调整为“辅助者”

AI 最初用于自然语言加规则和识别用户意图，随后扩展到普通聊天。但现场测试暴露了明显风险：

- “添加多条规则”可能被识别成查询；
- “模拟自动签核”曾错误触发真实签核；
- 对模拟行为的追问可能又被识别成查询；
- AI 接口超时、推理 token 占满或配置读取路径不一致时，飞书会误报 AI 不可用。

因此，当前安全原则改为：

- AI 永远不直接执行签核、拒签、全签或全拒；
- AI 判断用户可能想操作时，只提示可使用的明确指令；
- “模拟、测试、预览”优先进入只读流程；
- “为什么、怎么、解释”等问句优先作为自然聊天；
- 只有确定性的本地命令解析器能够进入签核动作。

这是整个项目中最重要的一次设计修正：AI 负责理解和建议，确定性程序负责执行。

### 7. 卡片、通知与可视化管理

飞书卡片先后出现按钮无动作、点击后重复回复、内容显示不全、表单回调 `200673`、动作值类型不一致等问题。后续统一了卡片回复格式，并将管理卡升级为可以原地刷新的 Card JSON 2.0。

通知策略也从“操作后统一发群”细化为：

1. 手动指令明确指定“发群”或“不发群”时，以手动要求为准；
2. 否则匹配独立通知规则；
3. 再看签核或拒签规则本身的通知设置；
4. 都没有匹配时使用用户默认设置，默认不发群。

签核和拒签分成不同颜色、不同卡片；拒签可以携带人工原因，也可以使用匹配规则中的默认拒签理由。所有群通知都必须在平台复查确认动作成功后才能发送。

### 8. 统计网页与独立提醒

项目后期增加了基于飞书 OAuth 的个人统计网页。用户只能查看自己的操作记录，并能按申请人、规则、类别、单位等条件筛选和导出 Excel。

此外，系统增加了“新增待手动签核提醒”：

- 功能可在设置卡片中单独开启；
- 第一次运行只建立基线，不批量发送旧数据；
- 后续只私聊提醒新增的待手动项目；
- 相同内容不重复提醒；
- 即使暂停自动签核，提醒功能仍可独立运行；
- 提醒只读，不会执行签核或拒签。

## 三、开发中最有价值的经验

### 1. 高风险动作必须与自然语言识别分离

签核和拒签会直接影响真实业务，不能仅因为 AI “大概理解了”就执行。自然语言可以用于帮助、解释和生成建议，但真正操作必须经过明确指令、快照确认和平台结果复查。

### 2. 测试模式必须贯穿整个系统

“模拟自动签核”不能只是界面上的提示，而要从消息路由、规则判断、提交模块到群通知全部保持只读。只要其中一层仍允许提交，就可能出现测试变成真实操作的问题。

### 3. 多用户系统要从一开始就隔离数据

账号、规则、组、设置、统计和待确认快照都必须绑定 `open_id`。仅在显示层隐藏他人数据是不够的，服务端查询也必须按当前 OAuth 用户过滤。

### 4. 通知应晚于平台复查

接口返回成功并不代表平台最终状态已经改变。当前做法是在提交后重新查询，确认申请已经从待签列表消失，再记录统计并发送通知。这比“提交后立即报成功”可靠。

### 5. 现场日志应少而有用

开发初期为了排查问题打印了大量信息，但长期运行会快速产生大文件。更合适的方式是记录首次异常、异常类型和关键上下文，对相同错误去重，并在恢复后清除异常状态。

### 6. 卡片交互要按飞书协议设计

卡片不仅是把文本变漂亮。按钮数据结构、表单字段、同步回调格式和三秒响应限制都会影响实际可用性。卡片结构必须有回归测试，不能只依靠人工点击验证。

## 四、实际使用心得

### 优点

- 用户可以直接在飞书完成查询、规则维护和设置，不必登录服务器；
- 自动签核、手动签核和待手动提醒可以按用户独立配置；
- 卡片展示比纯文本更清晰，特别适合完整待签内容和规则管理；
- 群通知能够区分签核与拒签，并显示操作人和拒签原因；
- AI 可以降低指令记忆成本，同时安全边界避免其直接操作；
- OAuth 统计网页方便个人复盘和导出数据。

### 使用时需要注意

- 第一次使用必须先私聊机器人登录签核平台；
- 修改规则后应先运行“模拟自动签核”，确认分类正确；
- 全签和全拒始终需要二次确认；
- 手动操作与规则结果相反时，需要再次确认；
- 自动签核暂停不代表待手动提醒也停止，两者是独立开关；
- 群通知默认关闭，需要在规则、通知规则或设置中明确开启；
- 服务器更新后应通过 `/health` 核对实际运行版本，避免旧 Gunicorn 进程继续提供服务。

## 五、当前流程概括

系统现在有两条主要入口：

1. **用户交互入口**：飞书消息或卡片进入回调服务，经过去重、身份判断和安全路由后，执行查询、管理或明确的人工操作。
2. **定时运行入口**：计划任务遍历已登录用户，在各自时间窗口和执行间隔内查询待签内容，先处理新增待手动提醒，再根据自动签核开关决定是否继续执行规则。

无论是人工还是自动操作，都遵循“查询最新数据 → 规则判断 → 必要确认 → 平台提交 → 重新查询验证 → 统计记录 → 按策略通知”的闭环。

## 六、结论与建议

这个项目的主要成果，不只是增加了更多命令，而是逐步把一个个人自动化脚本改造成了具备安全边界、用户隔离、可视化管理和运行审计的服务。

后续建议优先处理三项工作：

1. 每次发布统一更新代码版本、说明书、部署说明和压缩包，避免当前代码 `2026.07.24.2100` 与部分文档仍写 `2026.07.24.1700` 的情况；
2. 为消息路由、卡片回调、通知优先级和定时任务增加持续回归测试；
3. 将关键运行指标控制在少量、可追踪的日志中，并增加异常次数和最后成功时间的管理页展示。

## 七、从开发经历沉淀为 Skill

本项目的 Skill 不是飞书机器人运行时的一部分，而是给后续 AI 维护者使用的项目操作手册。它将开发过程中反复出现的工作分成三类：

- 将安全边界、模块职责和固定修改顺序写入 `SKILL.md`；
- 将规则结构、通知优先级和指令说明放入 `references/`；
- 将重复且容易出错的检查放入 `scripts/`。

开发 Skill 时，应先收集真实任务和事故，再提炼通用方法，最后才编写文件。完成后还要进行结构校验、项目测试和无历史上下文的真实任务验证。详细步骤见 `如何开发Skill_分析.md` 和 `Skill开发步骤流程图.svg`。
