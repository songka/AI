# BOMCheck 料号检测系统整改说明

编写日期：2026-06-30  
依据文件：`docs/任务交底书.md`、`docs/使用说明书.md`  
适用版本：`bomcheck-UI002`

## 1. 整改背景

根据任务交底书，当前版本已经完成桌面版窗口适配、Web 响应式优化、失效料号库弹窗优化、料号资源维护弹窗优化、账号权限、Web 查询等主要功能调整，并已完成基础语法编译和 Web 启动检查。

但交底书同时明确存在以下未闭环事项：尚未重新打包 exe、尚未完成目标电脑上的完整人工 UI 验收、现有部分文档或源文件存在中文乱码、典型 BOM 回归测试清单不足、Web 管理页表单校验和保存提示仍需完善。若直接交付，普通用户、资料维护者、UI 工程师、软件工程师和项目经理在使用、维护、验收、发布管理等环节都会遇到不同层面的疑问或风险。

本整改说明先从多角色视角提出问题，并给出整改方向、优先级和验收标准，作为后续实施整改和验收追踪的依据。

## 2. 多角色问题梳理

### 2.1 普通用户视角

1. 如何确认自己打开的是最新版本，而不是旧 exe 或旧目录？
2. 如果窗口仍然显示不全，用户应该先拖动滚动条、最大化窗口，还是联系维护人员？
3. BOM 执行完成后，结果文件保存在哪里、失败时应如何处理，说明还不够直观。
4. 查询无结果时，用户难以判断是关键词不对、料号库未更新，还是被屏蔽申请人规则过滤。
5. Web 版和桌面版入口并存，普通用户可能不知道该优先使用哪一个入口。
6. 默认管理员账号 `admin/admin` 出现在说明中，普通用户可能误以为可以随意使用管理权限。

### 2.2 资料维护者视角

1. 失效料号库、绑定料号库、重要物料、屏蔽申请人等数据文件缺少统一的维护规范和字段校验说明。
2. 多人同时编辑同一个 Excel 或 JSON 数据库时，可能发生覆盖、文件占用或数据损坏。
3. 修改资料前虽建议备份，但缺少备份路径、命名规则和恢复流程。
4. 绑定料号规则字段较复杂，`ALL`、`ANY`、`NOTANY` 等条件模式需要更多示例。
5. 屏蔽申请人规则的实际影响依赖处理逻辑，当前说明偏抽象，维护者难以评估改动后果。
6. 料号资源包含图片、模型、本地地址和网络地址，缺少资源命名、存放层级和链接有效性检查规范。

### 2.3 UI 工程师视角

1. 桌面版通过滚动容器解决窗口裁切，但需要确认不同分辨率、缩放比例和字体设置下是否仍然可用。
2. 弹窗默认尺寸和最小尺寸已经设定，但没有形成统一窗口设计标准。
3. Web 页面已处理响应式溢出，但还需要检查移动宽度、小屏窗口、长字段、超宽表格等极端情况。
4. 管理页保存成功、保存失败、权限不足、数据为空等状态提示需要继续统一。
5. 表格横向滚动虽然解决显示问题，但可能影响用户发现关键按钮或字段，需要优化重点信息层级。
6. 资料维护页面承担高风险操作，应增加更明确的确认、撤销或保存反馈。

### 2.4 软件工程师视角

1. 当前验证以 `py_compile` 和 Web 启动检查为主，缺少业务回归测试。
2. 数量列识别、失效料号替换、绑定料号统计、重要物料命中等核心规则需要固定样本验证。
3. Web 上传临时文件、结果文件、日志、账号库等运行时数据需要确认清理策略和异常恢复能力。
4. 桌面版与 Web 版复用业务逻辑，但入口差异可能导致配置、权限、文件路径行为不一致。
5. 文档提到部分中文乱码，若源文件或 README 编码混乱，后续维护容易误改或提交损坏内容。
6. 网络共享盘不可访问、Excel 被占用、配置文件路径错误等异常场景需要更明确的错误提示和日志定位。

### 2.5 项目经理视角

1. 当前交底书列出“已完成”和“未完成”，但缺少明确责任人、完成时间和验收结论。
2. exe 未重新打包属于交付阻断项，必须在正式发布前关闭。
3. 现场 UI 验收未完成，无法证明窗口优化已经覆盖目标用户环境。
4. 文档乱码会直接影响交付质量，应纳入发布前整改清单。
5. 历史版本目录需要清理，否则用户可能误用旧版本，导致“已修复问题仍复现”。
6. 需要建立版本号、变更说明、回退方案和现场验收记录，避免后续追责困难。

## 3. 整改目标

1. 保证用户拿到的 exe、源码、配置和文档版本一致。
2. 保证普通用户能够完成 BOM 检测、结果下载或查看、料号查询等基本操作。
3. 保证资料维护者可以安全维护关键数据，并能在误操作后恢复。
4. 保证桌面版和 Web 版在目标环境下界面不遮挡、不溢出、关键按钮可见。
5. 保证核心业务规则有典型样本回归验证。
6. 保证交付材料无明显乱码、路径错误、旧版本混淆和权限说明缺失。

## 4. 整改措施

### 4.1 版本与发布整改

1. 重新执行 `scripts/build_windows_exe.bat`，生成最新 `dist/bomcheck/bomcheck.exe`。
2. 在交付目录中增加版本说明，明确源码版本、打包时间、交付人员和适用环境。
3. 清理历史版本目录，仅保留当前稳定版和一个备份版。
4. 在 README、使用说明书和任务交底书中统一当前交付目录名称。

验收标准：
- 目标电脑运行的 exe 与当前源码改动一致。
- 用户无法在交付目录中误点旧版本 exe。
- 文档中的目录名、启动命令、访问地址与实际交付一致。

### 4.2 文档与编码整改

1. 统一将 Markdown、Python、模板、配置说明等文本文件保存为 UTF-8。
2. 修复 README、任务交底书、使用说明书中可能出现的中文乱码。
3. 增加“普通用户快速操作流程”和“资料维护者维护流程”两个简明章节。
4. 增加常见异常处理表，包括配置读取失败、Excel 占用、查询无结果、Web 登录失败、结果文件无法保存等场景。

验收标准：
- 在目标电脑使用常见编辑器打开文档时中文显示正常。
- 普通用户不看源码也能完成基本使用。
- 资料维护者能按说明完成备份、修改、保存和恢复。

### 4.3 UI 与交互整改

1. 在目标电脑分辨率和缩放比例下逐项验收桌面主界面、失效料号库、绑定料号库、料号资源维护、数据文件配置。
2. Web 端验收首页、查询页、任务页、管理页、表格页在非最大化窗口下的显示效果。
3. 对高风险操作增加统一提示，包括保存成功、保存失败、权限不足、数据格式错误、文件被占用。
4. 对超长料号、超长描述、超宽表格字段进行显示检查，必要时增加截断、换行、提示或横向滚动。

验收标准：
- 关键按钮不被遮挡。
- 表格可滚动，字段可识别。
- 保存、失败、权限不足等状态有明确反馈。
- 普通用户不需要猜测下一步操作。

### 4.4 数据维护整改

1. 为失效料号库、绑定料号库、重要物料、屏蔽申请人建立维护规范。
2. 明确数据文件修改前必须备份，备份命名建议为 `文件名_YYYYMMDD_HHMM_维护人`。
3. 对绑定料号规则增加示例，说明 `ALL`、`ANY`、`NOTANY` 的适用场景。
4. 增加多人维护限制说明，同一时间只允许一名维护者编辑同一个核心数据文件。
5. 建立料号资源命名和存放规范，明确图片、模型、本地地址、网络地址的维护要求。

验收标准：
- 维护者可以根据规范新增、修改、回退一条数据。
- 错误格式能被发现，不能静默进入正式库。
- 关键数据文件具备可追溯备份。

### 4.5 测试与质量整改

1. 建立典型 BOM 样本清单，至少覆盖正常 BOM、失效料号命中、替换料号、缺少必备料号、重要物料命中、数量列异常等场景。
2. 固定每个样本的预期结果，形成回归测试记录。
3. 对 Web 上传、任务执行、结果下载、临时文件清理进行验证。
4. 对网络共享盘不可访问、Excel 文件被占用、配置路径错误等异常场景进行验证。
5. 保留每次发布前的测试结论，记录测试人员、测试时间、版本和遗留问题。

验收标准：
- 每次发布前至少完成一轮核心业务样本验证。
- 失败问题有明确复现路径和处理结论。
- 未关闭问题必须在交付说明中标注风险和规避方式。

## 5. 优先级建议

| 优先级 | 整改项 | 原因 |
| --- | --- | --- |
| P0 | 重新打包 exe 并现场验证 | 不打包会导致源码修改不生效，属于交付阻断项 |
| P0 | 修复交付文档中文乱码 | 影响用户理解和正式交付观感 |
| P0 | 完成目标电脑 UI 验收 | 当前窗口问题需要在真实环境确认 |
| P1 | 建立典型 BOM 回归测试清单 | 避免后续修改破坏核心业务结果 |
| P1 | 明确数据维护和备份规范 | 降低资料库损坏和误改风险 |
| P1 | 完善 Web 管理页保存提示和表单校验 | 降低维护者误操作风险 |
| P2 | 抽象 Tkinter 通用滚动布局 | 降低后续窗口维护成本 |
| P2 | 清理历史版本目录并补充版本记录 | 降低误用旧版本和交接成本 |

## 6. 现场验收清单

1. 打开最新 `bomcheck.exe`，确认主界面可完整操作。
2. 打开失效料号库，确认表格、字段区、保存按钮、关闭按钮均可访问。
3. 打开绑定料号库，确认新增、编辑、保存流程可操作。
4. 打开料号资源维护，确认图片列表、预览区、自动生成区不遮挡。
5. 执行一份典型 BOM，确认结果文件正常生成。
6. 启动 Web 服务，访问首页、查询页、任务页、管理页。
7. 使用管理员账号登录，确认权限入口与保存反馈正常。
8. 检查任务交底书、使用说明书、README 是否无乱码。
9. 检查交付目录中是否存在旧版本 exe 或容易误点的历史目录。
10. 记录现场电脑分辨率、缩放比例、测试人员、测试时间和测试结论。

## 7. 结论

当前版本已经完成主要功能和界面适配整改，但仍处在“源码已改、交付闭环待确认”的状态。正式交付前应优先关闭重新打包、现场 UI 验收、文档编码修复、典型 BOM 回归测试和数据维护规范五类事项。

完成上述整改后，系统可以从“功能可运行”提升到“用户可交付、资料可维护、问题可追踪、版本可回退”的交付状态。
