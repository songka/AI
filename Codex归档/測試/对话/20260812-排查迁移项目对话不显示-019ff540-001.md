## 助手

多用户管理不要放在 `RouteLLM` 里做，放在 `NewAPI` 里做，会稳很多。

最适合你的分层是：

- `NewAPI` 管人、管钥匙、管额度、管分组
- `RouteLLM` 管“这次请求该走强模型还是弱模型”
- 上游模型只负责生成

也就是说，`RouteLLM` 应该尽量是“无状态路由器”，它不关心谁在用，只关心这条请求该去哪。真正的多用户控制，交给 `NewAPI`。

你可以这样理解：

```text
用户身份 -> NewAPI 识别
用户权限/额度 -> NewAPI 控制
任务难度 -> RouteLLM 判断
最终模型 -> NewAPI 转发
```

最实用的管理方式有 3 层。

1. 用户层

每个用户一个 `API Key`，或者至少按用户组发不同 key。

- `default` 用户
- `svip` 用户
- `vip` 用户

这样你不需要在客户端里硬编码逻辑，`Codex / OpenCode / Claude Code` 都只拿自己的 key。

2. 策略层

在 `NewAPI` 里按用户组绑定不同路由策略。

比如：

- `default` -> 低成本模型优先
- `vip` -> 强模型优先，弱模型兜底
- `admin` -> 全量可用，优先最稳模型

如果你想让 `vip` 也能同时用两个渠道，那就继续沿用你前面那套分组和优先级，但一定要把“谁属于哪个组”在 `NewAPI` 里固定住。

3. 任务层

`RouteLLM` 只负责单次请求判定，不负责用户管理。

比如同样是 `vip` 用户：

- 简单问答 -> `deepseek-v4-flash`
- 复杂代码审查 -> `gpt-5.6-terra`
- 带图片/截图 -> 直接强模型

这部分可以由 `RouteLLM` 根据任务难度做判断，但它不需要知道这是谁。

如果你担心“不同用户互相影响”，我建议你按这个原则来：

- 账号隔离放在 `NewAPI`
- 路由策略放在 `RouteLLM`
- 额度、日志、审计放在 `NewAPI`
- 客户端只认自己的 key

这样你以后加新用户，只要在 `NewAPI` 里新建一把 key、指定分组就行，不需要改路由器。

如果要更稳一点，我建议你用这个结构：

```text
用户A / 用户B / 用户C
  ↓
NewAPI 用户鉴权 + 分组 + 额度
  ↓
RouteLLM 任务路由
  ↓
NewAPI 渠道重写
  ↓
上游模型
```

这样有两个好处：

- 你可以精细控制每个用户能不能用强模型
- 你可以让所有客户端共享同一套路由逻辑，但权限不同
