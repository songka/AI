## 经验总结：Codex 迁移后"对话不显示"的根因与迁移要点

### 一、根因（一句话）

侧边栏对话列表由 app-server 的 `thread/list` 接口驱动。前端调用时传 `modelProviders=null`，app-server 会把它解释为**"只返回当前激活的模型提供商"**。

- 旧环境（账号登录）对话的 `model_provider` = `openai` / `myapi` / `custom` / `cc-switch-official` …
- 新环境（API Key）当前 provider = `newapi`
- 迁移后历史对话 `model_provider` 仍是旧值 → 被过滤 → 侧边栏为空

**实测数据**：修复前 `thread/list` 只返回 26 条（全 `newapi`）；把 `threads.model_provider` 全部归一到 `newapi` 后返回 114 条，侧边栏恢复。

---

### 二、侧边栏数据链路（迁移程序要覆盖这条链）

```
前端 Electron 侧边栏
   └─ JSON-RPC: thread/list
        params: { archived:false, modelProviders:null, sourceKinds:[], useStateDbOnly:true, sortKey:'updated_at' }
             └─ app-server (codex.exe) 读 state_5.sqlite 的 threads 表
                  过滤条件（关键）：
                    - archived = 0（归档区用 archived = 1）
                    - thread_source != 'subagent' 且 != 'ambient_suggestions'
                    - preview <> ''（部分路径）
                    - model_provider IN (当前激活 provider)   ← 本次根因
```

---

### 三、迁移必须处理的数据

| 文件 | 表/键 | 作用 | 迁移时要注意 |
|---|---|---|---|
| `~/.codex/state_5.sqlite` | `threads` | **侧边栏主数据源** | 见下方字段校验 |
| `~/.codex/sqlite/codex-dev.db` | `local_thread_catalog` | 目录同步缓存（次要） | 不是主数据源，但建议同步/重建 |
| `~/.codex/.codex-global-state.json` | `thread-project-assignments` | 对话→项目映射 | 必须一起迁移并合并 |
| 同上 | `local-projects` / `project-order` / `selected-project` | 项目列表与选中项 | 一起迁移 |
| `~/.codex/config.toml` | `model_provider` / `[model_providers.*]` | 当前激活 provider | 迁移目标机的 provider 名 |

#### `threads` 表字段校验清单

1. **`model_provider`（最关键）**：必须改成目标机当前激活的 provider 名。
2. `source`：必须是合法 source kind（`vscode`/`appServer`/`cli`/`custom`/`unknown` 等）；子代理线程 `source` 是 JSON，且 `thread_source='subagent'`。
3. `thread_source`：`user` / `automation` 会显示；`subagent` / `ambient_suggestions` 会被隐藏。
4. `preview`：不能为空（否则部分列表路径会过滤掉）。建议回退顺序：`preview` → `name` → `title` → `cwd` → `id`。
5. `archived`：0 显示在正常列表，1 进归档区。
6. `updated_at` / `recency_at`：必须是有效数字时间戳，用于排序。
7. `thread_section_id`：普通对话应为 NULL。

### 四、迁移程序的正确做法（建议）

1. **复制 `state_5.sqlite` 后，重写 `model_provider`**：
   ```sql
   UPDATE threads
   SET model_provider = '<目标机当前provider>'
   WHERE model_provider != '<目标机当前provider>';
   ```
   `<目标机当前provider>` 从 `config.toml` 的 `model_provider` 读取（本例是 `newapi`）。

2. **同步项目映射**（否则会出现"项目回来了但对话不在项目里"）：
   - 合并 `.codex-global-state.json` 中的：
     - `thread-project-assignments`（thread_id → {projectKind, projectId, cwd}）
     - `local-projects`（projectId → {id, name, rootPaths}）
     - `project-order`、`selected-project`

3. **`local_thread_catalog` 可重建或同步**：它不是侧边栏主源，但如果要写，`model_provider` 也要统一成目标 provider。

4. **重启应用**：即使数据改对，运行中的 app-server 和前端有内存缓存，必须完全退出（含托盘）再打开才会刷新。

### 五、迁移完成后的自检方法（强烈建议内置到迁移程序）

最可靠的方式是直接问 app-server（跟 UI 走同一条路）：

```
运行: codex.exe -c features.code_mode_host=true app-server --analytics-default-enabled
然后 JSON-RPC(stdio):
  initialize
  thread/list {archived:false, cursor:null, limit:200,
               modelProviders:null, sourceKinds:[],
               sortKey:'updated_at', useStateDbOnly:true}
```

预期：返回的 `data` 条数 ≈ `SELECT COUNT(*) FROM threads WHERE archived=0 AND thread_source!='subagent'`。

或者简单 SQL 自检：

```sql
SELECT COUNT(*)
FROM threads
WHERE archived = 0
  AND thread_source NOT IN ('subagent','ambient_suggestions')
  AND model_provider = '<目标机当前provider>';
```

### 六、这次走过的弯路（避免重蹈）

1. **一开始误判为 `local_thread_catalog` 同步被禁用**：去填充该表后侧边栏仍为空。实际上 `thread/list` 读的是 `state_5.sqlite.threads`，`local_thread_catalog` 是次要缓存。
2. **只重启不修数据没用**：重启不会自动重建被 provider 过滤掉的列表。
3. **最有效的定位手段**：不要猜 UI 逻辑，直接 spawn app-server 二进制、发 `thread/list` 请求，看到的就是 UI 会拿到的数据。用 `modelProviders` 的多种取值做对照，立刻锁定了 provider 过滤。

如果把这些点写进迁移程序，核心其实就是一句话：**迁移 `threads` 时把 `model_provider` 重写成目标机当前激活的 provider，并同步项目映射，然后用 `thread/list` 自检通过再收工。**
